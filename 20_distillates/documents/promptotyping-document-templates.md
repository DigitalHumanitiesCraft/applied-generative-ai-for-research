# Distillate: Promptotyping document templates

The template set that fixes what each document type of a Promptotyping knowledge base holds, whom it addresses, when it comes into being, when it is superseded, and what does not belong in it. It supplies the vault with the operative detail behind the paper's three-part document typology, including the routing of a function through the file name, the separation of declarative from action documents, and the boundary conditions each template states for itself.

## Core statements

- The index document of a knowledge base is called `INDEX.md`, lies in the `knowledge/` folder, and opens up the document register, the reading order, the storage zones, and the constitutive terms and abbreviations for human readers and agents alike. [[10_markdown/documents/promptotyping-document-templates#^p0003]] ^t01
- The index carries only from the point at which a knowledge base holds more than three documents, and its only update obligation is consistency against the real folder content, because an index that loses that consistency is worse than none, since it creates false confidence. [[10_markdown/documents/promptotyping-document-templates#^p0005]] ^t02
- The index document addresses a human reviewer, a newly set up coding agent, and the person responsible for the project returning after weeks, and it answers which documents exist, which routing question each path serves, in which order they are read, and which terms are constitutive. [[10_markdown/documents/promptotyping-document-templates#^p0006]] ^t03
- The project document is the canonical charter of a Promptotyping project, abstracted from concrete project overviews, and a public README may derive from it without replacing `knowledge/project.md`. [[10_markdown/documents/promptotyping-document-templates#^p0049]] ^t04
- The charter template carries for projects that process or produce a delimited material, that sit in an institutional, methodological, or technical context which is not self-explanatory, and that have defined functions whose description differs from the description of what is deliberately not provided. [[10_markdown/documents/promptotyping-document-templates#^p0050]] ^t05
- The plan document is the forward-looking process document of a knowledge base, the counterpart of the backward-looking journal, and it orders outstanding work into phases and milestones with entry and exit conditions anchored against the specification. [[10_markdown/documents/promptotyping-document-templates#^p0104]] ^t06
- The plan is delimited against its neighbours by direction and by subject, in that the journal is retrospective and is never rewritten while the plan is prospective and is carried forward, and the specification says what is built and why while the plan says when and in which order. [[10_markdown/documents/promptotyping-document-templates#^p0109]] ^t07
- An exit condition of a milestone states how completion is recognised, is anchored against an acceptance criterion, a quality gate, or a decision of the specification, and is formulated as a done-when statement rather than as a declaration of intent. [[10_markdown/documents/promptotyping-document-templates#^p0128]] ^t08
- The data document carries the epistemic responsibility for the material a project processes or produces, and it answers what the data are, where they come from, how they are modelled, and where the material stops carrying. [[10_markdown/documents/promptotyping-document-templates#^p0161]] ^t09
- The data document addresses a reviewer who wants to judge data quality, a coding agent that is to process or transform the data, and a domain expert who wants to follow the selection logic, and it makes transparent what the data support and what they do not. [[10_markdown/documents/promptotyping-document-templates#^p0165]] ^t10
- The provenance section of the data document records, per source, origin, capture logic, licence, provenance, and capture period, and where several sources are used it explains the relation between them. [[10_markdown/documents/promptotyping-document-templates#^p0178]] ^t11
- The domain-knowledge function carries as soon as a project makes a disciplinary or methodological stipulation that follows neither from the material nor from a software requirement, such as editorial guidelines, an encoding mapping, a coding manual, an ontology definition, or a calculation logic that a domain expert answers for. [[10_markdown/documents/promptotyping-document-templates#^p0207]] ^t12
- The domain-knowledge function separates a reasoning layer that carries theoretical framework, research questions, and methodological decisions with academic sources from a domain rule set that carries the normative detail of annotation, mapping, and calculation, and the two are split into separate files once they develop their own update rhythms and reader groups. [[10_markdown/documents/promptotyping-document-templates#^p0211]] ^t13
- The costliest decay pattern of a domain rule set is the schematically outdated rule set that continues to describe a superseded schema as current while the operative team already works against the new one, so a schema change carries the rule set with it in the same working step. [[10_markdown/documents/promptotyping-document-templates#^p0212]] ^t14
- A coding agent reads the domain rule set before it generates annotation or calculation code, so that a vague rule layer produces annotations that miss the intended semantics. [[10_markdown/documents/promptotyping-document-templates#^p0214]] ^t15
- User stories in the form of a role, a goal, and a benefit are the bridge between Scholar-Centred Design and implementation, arise typically in the Preparation or Exploration phase from sessions with domain experts, and are refined iteratively. [[10_markdown/documents/promptotyping-document-templates#^p0268]] ^t16
- The specification document consolidates requirements, epics and user stories, functional scope, and decisions into one file and answers the what and why of a project in one place. [[10_markdown/documents/promptotyping-document-templates#^p0323]] ^t17
- The four questions of the specification are held in one document because their answers are interlocked, in that a story motivates a requirement, a feature implements it, and a decision justifies why that feature is built this way, so that separating the layers risks a change in one layer silently ageing the others. [[10_markdown/documents/promptotyping-document-templates#^p0327]] ^t18
- A requirement of the specification is a recorded expectation of the system in formal, checkable language with an acceptance criterion, numbered as a functional or non-functional requirement, while the narrative user-facing form of the same matter is the user story. [[10_markdown/documents/promptotyping-document-templates#^p0338]] ^t19
- The architecture document carries the technical realisation of the system, covering stack, components, data flow, external models and services, and security and accessibility measures, and it is read by the agent before code is generated, so that a description too vague produces code that ignores the intended layers. [[10_markdown/documents/promptotyping-document-templates#^p0365]] ^t20
- A technology baseline carries technology decisions for a whole family of artefacts and is published centrally, so that a project instance references it by URL and its own architecture document records only the project-specific stack and the deviations from the baseline. [[10_markdown/documents/promptotyping-document-templates#^p0401]] ^t21
- The document type of a template is decided by the diagnostic question of the typology, which asks which document has to be revised when the output is wrong, so that a rule set binding how something is built counts as an action document even where it is written as reasoned rules rather than imperatives. [[10_markdown/documents/promptotyping-document-templates#^p0406]] ^t22
- The design document is declarative knowledge that records design stance, design system, interaction patterns, and visualisation logic, and the socialisation of a coding agent on the aesthetic layer arises through composition, in that the action document points at the design document as the source of values and translates it into imperatives. [[10_markdown/documents/promptotyping-document-templates#^p0436]] ^t23
- Keeping the design document declarative and letting the action layer carry the imperatives prevents a knowledge document from changing its analytical type. [[10_markdown/documents/promptotyping-document-templates#^p0439]] ^t24
- The integration document holds the currently valid contract at a project boundary, covering exchange format, responsibilities, and acceptance criteria, and it is delimited against the architecture document, which describes the internal structure of one's own project, against the handoff document, which carries incoming deltas until they are integrated or discarded, and against the journal, which evidences the completed transition. [[10_markdown/documents/promptotyping-document-templates#^p0474]] ^t25
- Where both sides of an interface describe the same contract, exactly one side must be declared the source of truth and both must reference each other, because one-sided linking was the consistency defect the template extraction found. [[10_markdown/documents/promptotyping-document-templates#^p0475]] ^t26
- The testing document carries the test strategy, its guarantees, its deliberate gaps, and the reproducible run commands, and its trigger is the need to make the strategy as a whole intelligible rather than the mere existence of individual tests. [[10_markdown/documents/promptotyping-document-templates#^p0520]] ^t27
- The testing document tells the agent in which form a new guarantee has to be secured, and thereby lifts a sign-off from an assertion that something holds to a measurement that a check is green. [[10_markdown/documents/promptotyping-document-templates#^p0525]] ^t28
- The verification document carries the adversarial examination of a project's own empirical and novelty claims against the raw data, and its trigger is the externally effective claim rather than the mere existence of data, so a project that only explores internally needs none. [[10_markdown/documents/promptotyping-document-templates#^p0576]] ^t29
- A verification document comes into being before the first externally effective claim leaves the project, because a verification supplied afterwards examines an already published formulation and can only restrict it. [[10_markdown/documents/promptotyping-document-templates#^p0577]] ^t30
- Quality assurance examines system behaviour against the specification while verification examines whether substantive claims are covered by the raw data, and the journal holds the chronological course of decisions while verification is the synchronous, antagonistic examination of one claim against its evidence. [[10_markdown/documents/promptotyping-document-templates#^p0578]] ^t31
- The stance of the verification document is adversarial, in that the procedure attempts to refute its own claims rather than to confirm them, it addresses the operator as Critical Expert who decides on the release of externally effective formulations, and the binding rule is that such claims may be used only in the form the verification licenses. [[10_markdown/documents/promptotyping-document-templates#^p0579]] ^t32
- The verification document names the units under examination and the reference standard against which they are held, such as statements against character-exact full texts or transcriptions against verified references. [[10_markdown/documents/promptotyping-document-templates#^p0591]] ^t33
- The limits section of a verification document states what the procedure structurally cannot achieve, such as that ground-truth-free procedures measure plausibility rather than correctness, that agreement among several models guarantees no truth, and that hallucinations below the detection threshold can pass, and the section is constitutive, because a verification without named limits is incomplete. [[10_markdown/documents/promptotyping-document-templates#^p0599]] ^t34
- The action document of a Promptotyping repository lies in the repository root rather than in the knowledge folder, socialises the coding agent through imperative rules that point at the declarative knowledge base, and carries no knowledge of its own, because it routes to knowledge and translates it into imperatives. [[10_markdown/documents/promptotyping-document-templates#^p0620]] ^t35
- The action document is injected automatically at every session start, which makes drift more expensive there than in any other document, so every line derivable from the code or from the knowledge base is deleted rather than maintained. [[10_markdown/documents/promptotyping-document-templates#^p0622]] ^t36
- The diagnostic grid of the convention assigns a formally wrong output, a break in style, or an ignored prohibition to the action document, and a substantively wrong output to the knowledge documents, which are then examined rather than patched in the action layer. [[10_markdown/documents/promptotyping-document-templates#^p0623]] ^t37
- The agent reads the index of the knowledge base at every session start, then the handoff document, and then the task-relevant declarative or action document, and the routing must point at repository-internal sources, because a repository whose method knowledge lies only in an external vault is blind in a session without access to that vault. [[10_markdown/documents/promptotyping-document-templates#^p0631]] ^t38
- The portable method core of the action layer comprises knowledge-base routing, handoff processing, journal provenance, the rules of the checking layer, design principles, scope, and the hierarchy of truth, and it is independent of the particular coding agent, so that only the tool block is exchanged when the agent changes. [[10_markdown/documents/promptotyping-document-templates#^p0662]] ^t39
- The journal is a curated retrospective provenance index that evidences transitions belonging together in substance, while current contents remain in the declarative, action, and process documents responsible for them. [[10_markdown/documents/promptotyping-document-templates#^p0681]] ^t40
- A journal entry arises per transition belonging together in substance and records whether the result was integrated, discarded, or corrected, and the journal carries no current project status, no open tasks, and no detailed check results. [[10_markdown/documents/promptotyping-document-templates#^p0634]] ^t41
- The journal is condensed when repetition, copied durable knowledge, completed open lists, scattered reasons for decisions, or an over-expensive regular reading context impair its provenance function, and neither its length nor the number of its entries triggers condensation on its own. [[10_markdown/documents/promptotyping-document-templates#^p0683]] ^t42
- The handoff document is the mandatory process inbox of a project, carries open handover points alone, and remains valid as an inbox in an empty state. [[10_markdown/documents/promptotyping-document-templates#^p0723]] ^t43
- Processing a handover point integrates durable content first into the responsible declarative or action document, then writes a short entry in the journal naming subject, source, target, and result or reason for rejection, and then removes the point completely. [[10_markdown/documents/promptotyping-document-templates#^p0729]] ^t44
- A dated exceptional handover state may be kept alongside the process inbox as a frozen record without replacing it, and a durable research-to-operations contract follows the integration template instead. [[10_markdown/documents/promptotyping-document-templates#^p0725]] ^t45
- The report document is the humanly curated project status report for an external addressee, carries scope and date in its file name, and lies among the dated snapshots. [[10_markdown/documents/promptotyping-document-templates#^p0752]] ^t46
- The report answers a third party without prior knowledge of the repository what was done in the reporting period, where the project stands on the reporting date, which robust results are available, and what happens next, which distinguishes it from every other document type of the method, whose addressee is the coding agent or the project itself. [[10_markdown/documents/promptotyping-document-templates#^p0755]] ^t47
- The report is separated from the journal by lifecycle and degree of curation rather than by content, in that the journal carries continuous chronological entries for internal addressees while the report is a single editorially condensed state without a narrative of the course of work, and the report quotes from the journal while the journal never references the report. [[10_markdown/documents/promptotyping-document-templates#^p0756]] ^t48

## Terms

- **Naming Contract**: the rule that the file name is the primary routing signal of a document, so that a single carrier of a function takes the plain function name and a specialisation takes a subject prefix. [[10_markdown/documents/promptotyping-document-templates#^p0566]]
- **Routing Question**: the question a document answers, recorded in the document matrix of the index so that an agent can decide which file to open. [[10_markdown/documents/promptotyping-document-templates#^p0006]]
- **Method core**: the portable part of the action layer, independent of the particular coding agent. [[10_markdown/documents/promptotyping-document-templates#^p0662]]
- **Process inbox**: the running process document that carries incoming deltas still to be examined, integrated, or discarded. [[10_markdown/documents/promptotyping-document-templates#^p0741]]
- **Quality gate**: a checkpoint defined in the specification, made up of mechanical and human checks, to which an exit condition of a milestone can be bound. [[10_markdown/documents/promptotyping-document-templates#^p0150]]

## Open questions

- The templates are written in German with English function names, while the manuscript is written in English with a German parallel version. Which German term of a template is carried into the book as a technical term, and which is translated, is undecided.
- The templates describe a document set that has grown well beyond the three types the paper names. Whether the book presents the full set or the paper's typology with the templates as its instantiation is a decision the outline leaves open.
- The templates cite named projects as their empirical basis. Which of those projects the book may name, and in which form, is not settled here.

## Appraisal

The templates are the operative counterpart of the paper. Where the paper states that the document types are organisational heuristics rather than a prescribed file structure, the templates show what a worked-out instance of that heuristic looks like after several revision rounds, including the boundary conditions each document type states against its neighbours. Their evidential character differs from the paper's. A template is a normative document that says how something should be written, so a statement drawn from it witnesses the current state of a convention and never the practice that follows it. Their version histories record which rules were introduced, tightened, or withdrawn on which date, which makes the set usable as evidence that the method's documentary layer was revised in response to observed defects. Where the book needs claims about how well the templates work in the hands of others, this source is silent.
